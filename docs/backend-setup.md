# Backend setup

## Requirements

- Node.js 20.9 or newer for the application; Node.js 24 is required for the built-in test runner's TypeScript module stripping used by the existing and new tests.
- A Supabase project with its Postgres database and Auth enabled.
- A GitHub OAuth application configured as the Supabase Auth provider.
- `SUPABASE_SERVICE_ROLE_KEY` is needed for server-managed profile/listing creation, release revalidation at submission, and pending-review state transitions. It is used only by server modules and must never use a `NEXT_PUBLIC_` prefix.

Set local values in `.env.local` (ignored by Git):

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<publishable-key>
APP_URL=http://localhost:3000
SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
```

The GitHub OAuth client ID and secret are configured only in Supabase Auth → Authentication → Providers → GitHub; they are not application environment variables. `.env.example` contains safe placeholders only. `.env.local`, `.env`, and environment-specific `.env.*` files are excluded from Git.

## Database migration

The schema is defined in the ordered migrations under `supabase/migrations/`, including `202610170002_publisher_revisions.sql` for private draft/review snapshots and transactional approval. It is additive and seeds the marketplace categories. Apply it to a fresh project through Supabase SQL Editor, or with the Supabase CLI after linking:

```sh
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push
```

Review the migration plan and back up production data before applying any schema change. Do not run `db reset` against a shared or production project.

The API row type mirror is currently handwritten in `src/types/database.types.ts`; it was not generated by the CLI. Once a linked/local Supabase database has the migration applied, generate and review a fresh schema snapshot:

```sh
npx supabase gen types typescript --linked > src/types/database.generated.types.ts
```

Compare the generated schema with the checked-in mirror before switching the client type import.

### Marketplace API returns 500 with PGRST205

The marketplace routes depend on the tables in the migration being present in the Supabase `public` schema. A terminal error such as `PGRST205: Could not find the table 'public.applications' in the schema cache` means PostgREST cannot see the required schema; it is not an RLS or client-side authentication failure. Confirm the migration has been applied to the Supabase project configured for this app. In Supabase SQL Editor, check `select to_regclass('public.categories'), to_regclass('public.applications');`; both results should be non-null. If the tables exist but PostgREST still reports `PGRST205`, run `notify pgrst, 'reload schema';` after the schema update. Do not work around this by disabling RLS or returning fixture data from the live API.

## GitHub OAuth configuration

1. In GitHub, create an OAuth App. Set its homepage URL to the application origin and its **Authorization callback URL** to `https://<project-ref>.supabase.co/auth/v1/callback` (the Supabase Auth callback, not the app route).
2. In Supabase Dashboard → Authentication → Providers → GitHub, enable GitHub and enter that GitHub OAuth App's client ID and secret.
3. In Supabase Dashboard → Authentication → URL Configuration, set **Site URL** to the application origin. Add exact **Redirect URLs** for `http://localhost:3000/api/auth/callback` and each production app callback, such as `https://<app-domain>/api/auth/callback`.
4. Set `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `APP_URL`, and (for backend write operations) `SUPABASE_SERVICE_ROLE_KEY` in the local ignored `.env.local` or deployment's secret environment configuration. `APP_URL` must be only the canonical origin. Restart the app after changing local values.
5. Start the app, open `http://localhost:3000/api/auth/github` in a browser, approve GitHub access, and confirm the browser returns to the app. The handler asks Supabase for `read:user public_repo`; repository verification needs the resulting provider token.
6. With the same browser session, open `http://localhost:3000/api/auth/me`. A successful response contains the authenticated user ID and GitHub username. Do not copy or share session cookies.
7. Verify repository access using the same authenticated browser session. For example, open `http://localhost:3000/api/developer/repositories/verify?repository=<owner>%2F<repo>` for a public repository where the signed-in GitHub user has write access. A successful response confirms the backend could use the GitHub provider token; the token itself is never returned.
8. Send `POST http://localhost:3000/api/auth/logout` with the session cookie (easiest in the browser's DevTools Console on the app origin: `fetch('/api/auth/logout', { method: 'POST' })`). Then request `/api/auth/me` again; it should return `401`. Avoid copying cookies into logs or shared terminals.
9. If OAuth fails, check the server's `APP_URL`, GitHub's callback URL (Supabase `/auth/v1/callback`), Supabase's exact redirect allow-list entry (app `/api/auth/callback`), and the configured provider credentials. The app returns a generic `/?auth=failed` redirect for exchange failures.

Automated tests cover callback error handling, authenticated-user recognition, and safe missing-token errors; they do not perform a real OAuth exchange. Provider-token availability through the configured Supabase SSR session still requires the live repository-verification step above. If the token is absent, repository verification returns `GITHUB_TOKEN_UNAVAILABLE`; it does not accept public visibility as proof of ownership.

## Local development and checks

```sh
npm install
npm run dev
npm run typecheck
npm run lint
npm test
npm run build
```

Without Supabase env values, the frontend fixture mode can still be used, but backend endpoints requiring Supabase return `503`. The health endpoint performs an actual database query. OAuth, live RLS behavior, GitHub ownership verification, and deployment cannot be confirmed without external project credentials.

## Integration recipes

### Member 1: public marketplace

Set `MARKETPLACE_API_URL=http://localhost:3000/api` for the existing server-side adapter. Retrieve `GET /apps?limit=50`, follow pagination as needed, use `GET /apps/{slug}` for listing details, and `GET /categories` for category names/counts. These endpoints return only published data. Errors use the documented error envelope; a missing/unpublished slug returns `404`.

The UI's current fixture catalog remains the fallback when `MARKETPLACE_API_URL` is unset. Do not treat fixtures as database data. The real browse response is `{data, pagination}`; details are `{data}`. `docs/api-contracts.md` is the field-level contract.

### Member 3: connected publishing portal

The portal now uses the authenticated APIs. Sign in through `/api/auth/github?next=/developer`, verify repository permissions, save a complete draft, and submit for review. Dashboard list/detail reads, optimistic saves, review withdrawal and published updates use the new private revision endpoints. See [member-3-contracts.md](./member-3-contracts.md).

Apply both migrations first. A missing revision schema produces an actionable `503 MIGRATION_REQUIRED`; the portal must not fall back to claiming a local draft is saved on the server. Browser recovery drafts remain separate and require explicit migration to the signed-in account.

## Moderation, deployment, and limits

There is intentionally no public admin endpoint or seeded admin role. Review and publication changes must be made by a trusted database operator or a future separately authenticated moderation service. For a manual review in Supabase SQL Editor, inspect the row and its repository/releases first; publish with a narrowly targeted statement:

```sql
select id, application_id, version, snapshot
from public.application_revisions
where status = 'pending_review';

-- Run only after reviewing that revision's repository, licence and selected files.
select public.approve_application_revision('<reviewed-revision-uuid>');
```

Approval applies public metadata, screenshots and selected installers in one transaction. A published update leaves its previous public version untouched until approval. Do not publish by directly setting `applications.status`; doing so skips materializing the reviewed snapshot. The database trigger, function grants and RLS block ordinary authenticated users from approving, promoting or featuring listings. Do not grant the service role to a browser or ordinary developer.

Vercel must provide the two public Supabase configuration values and the service-role key as encrypted server-side environment variables. Configure exact production redirect allow-list entries in Supabase. Migrations are applied separately; deploy does not automatically modify the production database.

GitHub uses bounded request timeouts and surfaces rate limits. No globally distributed API rate limiter is configured; the report table allows one report per authenticated user per listing. Release binaries remain hosted by GitHub and the API returns validated official URLs without proxying or executing them. No security scan or software-safety claim is made.
